# 自适应网络优化工具（Adaptive Network Optimizer）

**v0.3.9 · Windows 11 · 简体中文 · 只读实验与参数建议原型**

不依赖第三方 Python 库，不需要管理员权限，不修改注册表、DNS、MTU、防火墙、代理或 TCP 参数。

## 启动

需要 Python 3.10+（含 Tkinter）。如果尚未安装，可在 PowerShell 运行 `winget install --id Python.Python.3.13 -e`，完成后重新打开终端。解压本项目，双击 `start.cmd`，或在项目目录执行 `python app.py`。

## 测量过程

1. 读取 Windows 已连接网卡、DNS、默认路由、接口 MTU。将已连接 IPv4 网卡的 DNS 纳入比较，不假设它们就是浏览器实际使用的解析器。
2. 以同一批公开域名对各候选 DNS 执行 A 记录查询；轮换查询顺序，重复 3 或 5 次。直接向 UDP 53 查询，遇截断时尝试 TCP；验证交易 ID、问题、响应及 A/CNAME 记录。DNS 服务商可以记录查询，请勿输入私人/内网域名。
3. 统计每组成功次数、延迟中位数、P95（最近秩法）。只对全部成功的组推荐；当现有 DNS 的中位数不超过最快者的 110% + 2ms，且 P95 不超过最快者的 120% + 5ms，优先保留现有 DNS。阈值为第一版保守策略，不是网络标准。
4. 分别向 Cloudflare 的 IPv4、IPv6 地址 TCP 443 建立连接，记录 5 次连接结果。仅代表这两个目标的可达性和 TCP 握手耗时，不表示网站速度，也不是严格的网络层丢包率。
5. 可选探测指定公开 IPv4 目标的 MTU：Windows `ping.exe -4 -f -l`，每种载荷尝试 3 次；根据三次均成功的最大探测包估计路径可通过大小（载荷 + 28 字节）。仅覆盖至 1500 字节；小包无法稳定通过时不提供结果。ICMP 过滤、随机丢包及路由变化均可能干扰估计。
6. 在 `Downloads/AdaptiveNetworkOptimizer/` 创建独立报告目录，导出 `report.html`（图表和摘要）、`report.json`（含原始样本、网络配置与警告）、`dns_samples.csv`、`dns_summary.csv`。报告仅保存在本机，但含本地网卡、DNS 和路由等信息，分享前请检查。

## 边界与验收

- DNS 候选仅测试直接 IPv4 DNS UDP/TCP 53，不测试 DoH、DoT、IPv6 DNS、系统缓存或代理内的解析。不同解析器可能返回不同 CDN 地址。没有 DNSSEC 验证，不承诺查询未经透明转发或干扰；解析延迟低不等于下载吞吐量高。
- 不自动选择双 DNS 配对，不修改系统设置，不覆盖企业/VPN 的分流或私有解析规则。
- MTU 探测仅为特定路径估计，不自动推荐网卡 MTU。若高载荷失败，不能直接认定是 MTU 太大。
- 尚未实现 TCP 拥塞控制寻优、代理节点寻优、配置事务及回滚；这些应单独验收。
- `python -m unittest -v`：本地模拟 DNS UDP/TCP 服务器和确定性数据测试，无需外网。Linux 环境下通过；Windows GUI、真实网络、PowerShell 系统信息采集、Windows ping 输出解析仍需实机验收。

## v0.2.0：实际网络性能基准

- 默认开启 HTTPS 与 ICMP；TCP 443 对 Cloudflare、Google、Quad9 各一组 IPv4/IPv6 公共地址分别测 5 次，统计中位、P95 和相邻成功样本的绝对差均值（不跨失败样本，不是 RFC 定义的单向抖动）。
- Windows PowerShell/.NET Ping 返回结构化状态，统计每个目标的 ICMP 无应答率、RTT 和波动。ICMP 可能被防火墙、代理或目的端限速/过滤，不能等同于物理链路丢包率。全为本地异常时标为不可测。
- HTTPS 使用系统可用 curl，默认保留环境代理规则，不强制直连、不关闭证书校验、不跟随重定向、不重试。测量 Cloudflare 零字节端点、Google 204 和 GitHub API zen；吞吐量仅用 Cloudflare 官方测速接口固定 1/2/4 MiB，每组 3/5 轮、轮换顺序。缺少 curl 时跳过 HTTPS，保留其他数据。
- 解析 curl 累计计时，计算 DNS、TCP、TLS 阶段差值、TTFB、总耗时；代理 CONNECT 可能计入 TLS、TCP 可能连接代理、DNS 可能为本地代理。只有 2xx、退出码正常、字节数与预期及本地文件一致、计时有效才计入统计。有效 Mbps = 字节×8/总秒数/10^6；正文 Mbps 使用总时间减 TTFB，过短时不估计。403/429 停止该目标（Cloudflare 两个端点一起停止）。固定小样本并非最大带宽或长期速度测试。
- 默认测速正文计划 3 MiB，加上小请求；设置上限、请求超时和文件体积监控，临时文件自动清理。旧版 curl 对未知长度的限制可能有滞后，不承诺硬流量上限；取消最多等待当前有超时的探测返回。
- 即使 DNS 推荐被拦截，也保留当前实际路径的 HTTPS/TCP/ICMP 观测。记录性能前后配置快照及环境标记、测试计划和目标；快照一致不证明代理节点或路径未变化，不自动跨报告判断改善。`report.json` 增加 performance、performance_baseline、snapshot_after_performance；HTML 增加性能表，四个 performance_*.csv 导出原始或汇总数据。
- 仍为只读，不改网络配置；代理节点、用户身份、浏览器使用的实际协议未必可见。IPv6 多目标失败也不能证明系统完全不支持 IPv6。没有实现独立基线自动比较、代理节点优化、上传测速或安全回滚。
- 参考：curl https://curl.se/docs/manpage.html；Cloudflare 测速接口 https://github.com/cloudflare/speedtest；Google DNS https://developers.google.com/speed/public-dns/docs/using；Quad9 https://docs.quad9.net/services/。

## v0.2.1：自适应采样与失败证据

- 下载先进行 128 KiB 预探测，按实测速率选择 64 KiB 至用户上限的固定样本，预探测不参与正式统计。正式样本最多补测两次；阶段预算 210 秒，计划正文预算为 128 KiB + (轮数 + 2) × 上限，非硬流量上限。
- curl 失败记录退出码、阶段原始计时、已接收字节和分类；仅完整成功样本计入速度。TCP 记录异常类型、errno、winerror；ICMP 保留异常类型、HResult、可用的 socket 错误码，异常样本不纳入无应答率；IPv6 ICMP 不可用仍不等于丢包。
- 正式下载质量要求成功数不少于设定轮数、完成率至少 80%、成功速度最大值不超过最小值两倍、样本大小及 HTTP 版本一致。阈值为保守工程策略，非统计置信保证；即使通过也仅是候选基线，不自动调参。
- 未改变系统设置，不保证识别代理实际节点或故障根因。真实网络和 Windows GUI 仍需实机验收。

## v0.2.2：动态网络环境感知

- DNS 与性能实验期间每隔约 15 秒采集一次配置，最多 120 次周期采样，另保留三个阶段快照；采样串行、有超时，实际间隔包含采集耗时。记录 UTC 偏移时间、单调时钟秒数及采集耗时。监测失败、采样间隙和代理内部变化仍可能影响判断。

- 按接口索引/地址族及路由身份逐字段差分，记录观测时间区间；启用自动跃点数时的 metric 变化仅标记可能自动调整，不证明链路速率造成变化或修改者身份。链路遥测不作为配置签名字段。阶段内观察到配置变化或快照缺失时拒绝 DNS 推荐或性能基线（即使首尾恢复）。
- IPv6 诊断统计 WSAEACCES 10013，保留 ICMP NativeErrorCode，并读取防火墙配置、IPv6 网卡绑定和地址状态计数；不读取安全事件日志、不修改规则、不确定具体拦截组件。报告包含本地网络信息，分享前检查。
- JSON 增加 environment_monitor；HTML 增加差分和时间线，另导出 environment_changes.csv、adapter_link_timeline.csv、wlan_timeline.csv。周期采集会增加少量系统负载，不能证明采样间隙不变；仍不进行自动调参。

## v0.3.1：自适应寻优与鲁棒性增强

- 修正 curl 超时阶段归因：curl 的计时字段是累计时间，只有前置阶段确实完成时，才将后续计时解释为后续阶段。若 DNS 已完成、TCP 连接计时为 0、TLS 计时为 0，即使 `time_starttransfer` 因超时显示约 5 秒，也归类为 `TCP_CONNECT_TIMEOUT`，不再误报为数据传输超时。报告同时导出 `failure_phase`。
- 并发样本按每工作线程 64–256 KiB 自适应调整，目标正文测量窗口约 1.25 秒；依据上一轮成功样本估计正文速率，单轮样本大小变化限制在 2 倍以内。8 路并发不再固定把 512 KiB 平均分成 8 份。
- 连接超时依据上一轮成功请求的 DNS+TCP+TLS 阶段 P95 调整，范围 5–10 秒；完整传输超时仍限制为 20 秒。若缺少有效阶段证据，使用 5 秒默认值。
- 若正式轮次中存在失败或高波动候选，最多增加一组配对补测：同一轮内重新测试单并发基线和一个暂定最佳候选。补测仍受时间预算和正文预算约束，不无限重试。
- 候选比较增加同轮配对吞吐量比值，减少网络时段漂移的影响；综合评分权重为吞吐量 65%、请求成功率 25%、TTFB 10%。只有完整、合格且配对轮数足够的候选才参与推荐；选择达到最高综合分 95% 以上的最低并发度，且要求配对吞吐量至少提升 10%。
- 网络配置变化仍严格阻止推荐。链路遥测增加容差：信号强度变化不超过 5 个百分点、链路速率相对变化不超过 25% 时视为可容忍波动；适配器连接状态或媒体连接状态变化仍然阻止推荐。原始遥测变化仍保留在报告中，并标注容差内/超出容差。
- 3 轮并发实验的最坏正文预算约 13.5 MiB；5 轮约 21 MiB，另有 HTTP/TLS 协议开销。报告分别记录预算上限与实际预留量。实验仍只测当前 HTTPS 路径（可能经过代理/TUN），不代表物理链路，也不等同于 yt-dlp `-N`。
- 新增回归测试覆盖连接超时误分类、TLS/首字节/正文阶段分类、自适应样本、连接超时边界、配对补测、综合评分及无线遥测容差。GitHub Actions 在 Windows 与 Ubuntu 上执行回归测试。
- 不修改 DNS、MTU、代理、路由、防火墙或 TCP 配置；不自动应用任何参数。



## v0.3.2：实验可比性与因果有效性增强

本节替代 v0.3.1 的并发实验策略；历史版本说明保留。

- 先执行独立 128 KiB 单并发预探测，不进入正式统计。依据有效速度估计约 8 秒的目标工作量，将正式总正文固定在 128–512 KiB；连接超时由预探测决定并固定为 5–10 秒，完整请求超时固定 20 秒。每线程至少 64 KiB，慢网自动排除超出工作量的并发候选；未测候选不视为劣于已测候选。
- 每个候选每轮拥有独立相邻单并发基线，A/B 顺序交替、首轮随机，轮内随机候选顺序。整个正式实验（含最多一组补测）固定总字节数和超时。报告检查配对身份、序号相邻、成功字节数、HTTP 版本与 TTFB 等证据；不允许用不同条件的结果凑成配对。进程启动开销包含在有效吞吐量中。
- 以同对吞吐量比值的中位数为主要比较量。候选须完成全部计划配对，至少获得设定轮数个有效配对且有效配对率与候选请求成功率均≥75%；配对比值最大/最小≤2 且变异系数≤35%。原始基线波动保留，不单独因跨时段基线波动拒绝相对结果。存在条件/协议不一致则不能靠补测补救。失败配对永久保留，最多为一个不合格候选补测一整对。
- 相对效用 = 配对中位速度比^0.65 × min(配对完成率,候选请求成功率)^0.25 × min(1,配对中位 TTFB 基线/候选比)^0.10，单并发参考效用为1；不封顶、不填补缺失延迟。要求中位提升≥10%、至少2/3有效配对提升≥10%、效用>1，再选达到最高效用95%的最低并发；否则只在有合格比较时保守保留单并发。不是统计显著性或普适最优证明。
- 配置变化、连接状态变化、缺失无线指标、大幅速率下降仍拦截。已知 WLAN 信号全程波动≤5个百分点且连接状态不变时，显著速率上升只作旁证，不证明负载导致；同适配器、同时间窗、相同数值变化合并为一个观测事件，原始字段保留。小幅速率变化沿用25%容差，同时检查整个阶段的无线收发速率从此前峰值累计下降是否超过25%，避免逐步下降绕过保护。离散采样不能排除其他路径变化。
- 最大正文预算为 128 KiB + 2 × (轮数 × 高并发候选数 + 1) × 512 KiB（默认3轮10.125 MiB，5轮16.125 MiB）；另有协议及错误开销，非硬网络流量上限。600秒阶段预算可能截断5轮极慢实验，此时不推荐。HTTP 403/429 停止后续请求批次。
- 增加 tuning_pairs.csv、pilot、formal_plan、原始配对与候选排除证据。推荐仅适用于当前 Cloudflare HTTPS 路径和固定工作量，不代表持续带宽或 yt-dlp 参数。继续只读，不自动改系统。


## v0.3.3：序贯配对实验与自适应候选搜索

本节替代 v0.3.2 的采样策略。
- 独立执行三次 128 KiB 预探测，以至少两次完整成功样本的有效速度中位数校准；失败证据保留，成功不足两次则保守回退，且不正式推荐。若任一预探测失败，正式连接超时固定为10秒。
- 正式工作量仍固定 128–512 KiB。正式实验开始前，若最慢成功预探测速度估计可在16秒内完成较大样本，则尝试扩大候选范围，保证每线程至少64 KiB；不是对慢网强行测试8路。预探测不进入正式统计，所有候选/追加配对使用同一工作量和超时。
- 首先完成每个候选的最低轮数（GUI 3或5），随后只给尚未解决且可恢复的候选追加相邻配对，优先追加次数最少者，最多全局4对、单候选3对。若比值最大/最小已超过2，增加观测无法消除此硬限制，直接停止该候选；不删除异常样本，不放宽原质量阈值。
- 证据等级为工程规则而非统计置信概率：SUPPORTED_WITHIN_TESTED_SCOPE（所有已测候选达到质量要求且方向明确、至少两次成功预探测）、TENTATIVE（有初步比较但证据不足）、INSUFFICIENT。只有第一类且环境门槛通过才正式推荐。提升方向要求中位提升≥10%、至少2/3有效配对达到该提升、相对效用>1；无实质提升方向要求中位提升低于10%且至少2/3有效配对低于该阈值。未测候选不推断优劣。
- 批次保留原始浮点墙钟耗时；同等工作量速度比直接使用基线耗时/候选耗时，不使用显示舍入值。JSON 保留采样决策轨迹、停止原因、预探测、证据等级；增加 tuning_pilots.csv 与 tuning_sampling_trace.csv。
- 600秒阶段预算；正文预算上限 = 3×128 KiB + 2×(轮数×高并发候选数 + 最多4追加对)×512 KiB。默认3轮13.375 MiB，5轮19.375 MiB；额外协议开销不计入正文预算。预算不足则停止并报告证据不足/暂定，不保证所有轮次完成。HTTP 403/429 停止后续批次。继续只读，结果仅适用于当前路径和工作量。


## v0.3.4：细粒度配对环境有效性

- 预探测独立采集前后环境；正式每一对相邻基线/候选在开始前及结束后执行完整只读快照，保留周期采样。每批次记录 UTC 开始/结束时间及相对于同一监测单调时钟的秒数。前置采样须在批次开始前完成，后置采样须在最后批次结束后开始，分别限定5秒和30秒边界距离。未覆盖、缺失、超限不推断为稳定。
- 配对局部环境仍使用原有5个百分点信号、25%累积速率下降、网卡连接状态及配置规则。局部未验证的配对保留原始速度、请求、失败及环境证据，标记联合无效，仍计入分母；追加配对使用既有全局4对/单候选3对限制，不删除失败或根据测速成绩筛选环境。原始测量汇总和联合有效汇总分开。
- 全局配置变化、配置快照不完整、网卡连接状态变化或连接状态采集不足仍阻止最终推荐；无线信号波动仅在各配对窗口内作为正式质量门槛。预探测无线波动单独报告，不直接否决后续完整、稳定的配对；预探测仍须至少两次成功。每个已测候选须至少达到设定轮数个环境验证配对且覆盖率≥75%，并满足所有既有联合质量门槛。跨配对环境变化、代理内部切换和未采样事件仍可能影响比较；不证明因果关系或持续稳定。
- 独立记录 measurement_evidence_level、environment_evidence_level、最终 evidence_level 与 stop_reason。JSON保留配对窗口、监测索引、原始和联合证据；CSV增加批次时间和配对环境字段、tuning_measurement_summary.csv。
- 监测有额外开销：开始一对前为两次边界采样各预留52秒（含可能的周期采样锁等待），再预留两批请求的预算；不足则提前停止，正文预算不变。实际运行仍受系统调度和子进程退出影响，600秒为规划预算而非硬实时保证。不会修改系统配置。

## v0.3.6：负载感知实验调度与桌面报告体验

- 并发实验前启动独立低开销采样线程，每约1秒读取活动硬件网卡的64位累计收发计数；仅选择硬件接口且操作状态为 Up、媒体连接状态为 Connected 的记录。采样使用与周期性 PowerShell 完整快照分离的短锁和缓存接口索引，不等待完整快照锁。
- 低负载窗口定义为物理网卡总收发速率低于0.5 Mbps，连续3个有效采样区间（约3秒）。该阈值为工程启发式，不是链路空闲的绝对证明；多物理接口按接口速率求和，桥接/团队配置可能重复计数。采样不识别进程、浏览器、目的地址或流量来源。
- 每次预探测和每个相邻配对前均尝试等待低负载窗口。共享日常模式最多等待8秒，超时后继续采集但把对应预探测/配对标记为不可比较，不输出受干扰参数推荐；受控模式最多等待20秒，仍繁忙或采样不可用则跳过后续实验，不把繁忙窗口当作受控数据。配对开始完整快照后再次确认低负载状态；若快照期间负载升高则重新等待。取消信号会中断等待。
- 负载原始采样和调度决策写入 report.json、load_samples.csv、tuning_load_schedule.csv 与 HTML 报告。保留每次等待状态、等待时长、负载中位数/峰值及是否在繁忙窗口继续。低负载仅表示总物理接口流量低，不证明无后台任务或代理内部路径不变。
- 自动报告位置改为实际 Windows 桌面（通过 Windows Shell 桌面目录接口解析，支持桌面重定向/OneDrive）：Desktop/AdaptiveNetworkOptimizer/时间戳-运行ID/report.json。同目录保存 HTML、CSV；JSON 使用临时文件写入后原子替换，避免留下半份文件。GUI 新增“打开 report.json”和“打开报告文件夹”。
- GUI 统一 Microsoft YaHei UI（不可用时回退 Microsoft YaHei / Segoe UI），默认字号10–11pt，增加按钮内边距、表格行高、日志行距和窗口尺寸；HTML 报告统一中文字体栈、字号、行距与表格留白。
- 新增低负载窗口、繁忙超时、虚拟网卡排除、接口变化、桌面路径及调度门槛回归测试。仍然只读，不自动暂停应用或修改系统设置。


## v0.3.7：自适应负载基线与实验隔离

- 预探测及每一正式批次在实际请求前后记录同一单调时钟的实验边界（包括原生计数采集）。测速期间以及结束后1秒内的采样不得参与低负载判断或基线训练；使用前一计数采集开始至本次结束的保守时间跨度，排除跨界区间。启动下一预探测/配对前须取得3个全新连续非测速区间。同一配对的两个批次仍相邻，不插入冷却等待以免破坏时间可比性。低负载仅证明启动前观察到的负载低，不保证实验中无其他流量。
- 最近60个符合条件的非测速区间（总负载不超过0.5 Mbps）用于基线，至少8个后用经验下四分位数 P25 校准，动态阈值 = min(0.5, max(0.1, 2×P25+0.05)) Mbps。样本不足使用原0.5 Mbps上限；接口变化/计数不可用清空基线。阈值是保守工程启发式，不是物理链路空闲证明。高负载不能抬高上限。
- 保留8/20秒等待上限及现有实验时间、正文预算；共享模式超时仍可观察，不正式推荐；受控模式停止后续实验。实际请求开始前再次保存负载状态，若已失去低负载条件则该配对/预探测不能通过负载门槛。原始测量有效性与联合有效性分开保留。
- 对配对速度比极差超过2倍或控制条件不可比较、无法通过增加样本恢复的候选，提前停止后续正式轮次；其他候选照常运行。保留全部尝试和跳过原因。仅另行报告合格子集观察候选，单独验证子集配对环境覆盖及全局配置门槛；不能推断被排除候选较慢，不以子集结果替代正式推荐。
- 报告记录实验边界、冷却期、区间分类、动态阈值及原生计数边界间隔。计数区间要求时间有序、前后间隙各≤0.1秒、完整计数包络额外时间≤0.2秒；超限单独标注，不污染原始速度。JSON/CSV保留原始证据；桌面导出和中文字体保持不变。继续只读。


## v0.3.8 局部证据独立认证与跨次积累

每个候选分别与相邻的 1 路基线比较。GUI、HTML、JSON 及 `tuning_candidate_evidence.csv` 分别给出测量质量、配对环境与负载覆盖、认证方向。即使 4 路实验失败，2 路的合格配对仍然有效。局部认证也可能支持“未达到实质提升”。只有固定工作量下实际参与比较的所有候选都得出可靠结论，且全局环境检查通过，程序才会给出正式建议。

- 全局检查覆盖配置快照的完整性与稳定性、网卡连接状态及三次预探测的负载窗口。正式建议还要求预探测至少成功两次。共享使用模式仅产生观察结果。
- 单次与跨次分析共用质量判据。有效配对数至少达到计划轮数，配对完成率与候选请求成功率均须达到 75%，配对速度比的最大值/最小值不超过 2，变异系数不超过 35%。支持实质提升还须满足配对速度比中位数至少 1.10、至少三分之二的有效配对达到该幅度、综合效用高于 1。
- 程序在每次实验开始时分配运行编号。重复保存同一份结果只计一次。同一编号出现不同数据时保留原记录，并报告冲突。SQLite 使用事务与 WAL/FULL 同步。Windows 默认路径为 `%LOCALAPPDATA%/AdaptiveNetworkOptimizer/evidence.sqlite3`。其他平台使用 `$XDG_DATA_HOME/AdaptiveNetworkOptimizer/`，未设置该变量时使用 `~/.local/share/AdaptiveNetworkOptimizer/`。
- 历史库保存实验计划、配对指标、判定原因和上下文摘要。网络指纹保留 DNS 优先顺序，只保存 SHA-256 摘要。平台、目标、观测到的网络配置、工作量、超时、候选集合、计划轮数、使用模式和负载策略须一致。HTTP 协议按候选在整个会话中观测到的值分组。协议不明的失败尝试保留在相应网络与工作量的失败分母中。配置相同仍可能经历代理内部切换或无线链路变化。
- 全局环境或校准证据不足的会话仅存档。能确定环境的失败配对，以及已经启动一批但未完成另一批的配对，均计入尝试数。预算提前结束的实验可以贡献已完成的合格配对。正式的跨次建议要求当前实验已完成，本次和至少另一次独立运行都提供同方向证据，且所有已测候选均通过跨次验证。两个独立会话各自达到局部认证标准却得出相反结论时，暂缓推荐。
- `tuning_history.csv` 和 HTML 显示每个候选的独立运行数、本次有效配对数、累计尝试数、有效配对数和判定。数据库不可用时，仍可导出本次实验报告。旧版 SQLite 数据原位保留，缺少可核验会话编号或原始准入记录的历史仅作参考。原始实机报告保存在用户本机。工具继续以普通用户权限运行，只读取系统网络配置。


## v0.3.9 动态环境分层与历史证据时效管理

- 仅用正式配对前已经测得的固定 128 KiB 单路预探测速率进行历史状态分层。不使用任何候选收益、成功方向或最终推荐作为分层条件。至少两次有效预探测，最大/最小速率比不超过 2、变异系数不超过 35% 时，按中位速率所在的固定二倍区间 [2^k, 2^(k+1)) Mbps 分类；例如 [0.25,0.5)、[0.5,1)。未知或不稳定状态的会话仅存档，不借用历史证据；本次局部认证及单次推荐质量门槛不变。
- 历史上下文在原有网络配置、实验计划、负载条件、协议隔离之上增加状态区间与历史策略版本。旧策略上下文保留但不进入新版正式历史认证；不改写或删除旧库记录，不声称相同速率区间就代表相同代理节点或物理路径。区间边界和 24 小时窗口是保守工程策略，尚需实机验证，并非网络标准或统计置信保证。
- 历史窗口以当前测量会话开始的 UTC 时间为基准，包含过去 24 小时（边界含等号）。过期、晚于本次开始或时间不可核验的会话不参加本次历史统计；所有原始配对仍保存在原数据库。窗口内同条件失败、中断和冲突证据不因结果不利被筛除。重复保存仍按运行编号去重。
- JSON 的 history_store 提供策略标识、预探测状态、区间、离散程度及窗口基准。历史候选行、CSV、HTML 显示同一上下文内因时间排除的运行数；GUI 显示当前状态和窗口。历史质量判据、预算、用户批准边界均不变；仍不自动修改 Windows 网络配置。
